# Broadcast Control Lab — БКЛ

**Воспроизвести проблему. Проверить починку. Сохранить доказательства.**

БКЛ — независимая инженерная лаборатория для программ управления вещательным,
звуковым и видеооборудованием. Берём конкретную проблему, превращаем её в
повторяемую проверку, готовим исправление и, где реализована сборка, тестовый пакет.
Каждая починка пополняет инструментарий для следующих задач.

## Что уже работает

| Возможность | Для чего нужна |
| --- | --- |
| TCP-стенд | Отправлять ответы частями и с задержкой, разрывать соединение, принимать повторное подключение |
| UDP-стенд | Проверять отдельные бинарные пакеты, задерживать или пропускать ответы, наблюдать повторные команды |
| Журнал обмена | Видеть, что программа действительно отправила и что ей ответил стенд |
| Проверки конкретных версий | Повторять сценарий на зафиксированных исходниках |
| Паспорт кейса | Держать проблему, критерий успеха, версии, команды и ограничения в одном описании |
| Общий конвейер | По паспорту готовить исходники, запускать тесты и собирать пакет |
| Пакет доказательств | Получать результаты этапов, SHA-256 сборки и готовый текст отчёта для PR |

Стенды можно использовать со своими программами управления. Среди текущих
примеров есть модули Companion и Python-бэкенд AutoPTZ.

## Готовые примеры

- **[ATEN](cases/aten-2029/):** переменные входа и выхода матрицы, проверка диапазонов,
  совместимость сохранённых числовых настроек и вызова профиля. Семь проверок,
  тестовая сборка модуля и паспорт с отчётом.
- **[AutoPTZ](cases/autoptz-155/):** настоящий Python-бэкенд обменивается UDP-пакетами
  со стендом на localhost. Четыре проверки: остановка, Sony-ответ целым пакетом,
  короткий ответ и тайм-аут. Результат — диагностический отчёт и журнал пакетов.
- **[Intelix DIGI-88FS](FINDINGS.md):** команды маршрутизации, фрагментированные данные,
  приглашение авторизации без перевода строки и поведение без подключения.
- **[Sennheiser TCC2](FINDINGS.md):** ошибки SSC, корректные значения состояния,
  повреждённый JSON и границы секторов камеры.

ATEN уже использует общий паспорт. AutoPTZ пока запускается отдельным диагностическим
заданием; Intelix и TCC2 входят в исходный набор регрессионных проверок.

## Скачать починку

Откройте [Actions](https://github.com/iibaranov-IG/broadcast-control-lab/actions),
выберите успешный прогон нужного кейса и скачайте артефакты внизу страницы.
Для скачивания GitHub может потребовать вход в аккаунт.

| Задание | Что скачивать |
| --- | --- |
| BCL case pipeline | `aten-2029-test-build` — сборка; `aten-2029-report` — отчёт |
| BCL AutoPTZ UDP diagnostic | `autoptz-155-report` — результаты и пакеты |
| Broadcast Control Lab | `lab-report` — проверки BCL |

В отчёт кейса ATEN входят паспорт, `evidence.json` и `PR-REPORT.md`:
точные версии, результаты, контрольные суммы и задание владельцу железа.
При ошибке внутри запуска кейса сохраняется отчёт FAIL. Ошибки подготовки самого
задания видны в логах Actions. Срок хранения артефактов указан GitHub.

## Запустить самостоятельно

Нужны Git и Node.js 22+. Для диагностики AutoPTZ дополнительно нужен Python 3.12.
Сборка конкретного модуля использует точную версию Node из его паспорта.

```bash
git clone https://github.com/iibaranov-IG/broadcast-control-lab.git
cd broadcast-control-lab
npm run test:harness
node cases/aten-2029/test.mjs
python3 cases/autoptz-155/prepare.py
node cases/autoptz-155/test.mjs
```

Эти команды проверяют стенды и два примера. Полная установка AutoPTZ и зависимости
машинного обучения для его изолированной проверки не нужны.

Для `npm test` также нужны репозитории Intelix и TCC2 в каталогах `intelix` и
`tcc2`. Их родительский каталог задаётся через `LAB_SOURCES`, а версии указаны в
[workflow](.github/workflows/lab.yml). Готовое окружение собирается в Actions.

## Добавить свой кейс

[Описание формата](cases/README.md) и [паспорт ATEN](cases/aten-2029/case.json)
показывают, как задать проблему, ожидаемый результат, исходники, команды и артефакты.

```bash
node scripts/case.cjs list
node scripts/case.cjs validate aten-2029
```

Для полного запуска подготовьте свежий checkout исходников в каталоге и на версии
из паспорта, выберите указанную версию Node и выполните
`node scripts/case.cjs run aten-2029`.
Общий конвейер находит новые паспорта автоматически. Сценарий и проверки для
конкретного протокола нужно реализовать отдельно. [Руководство UDP](docs/udp-harness.md).

## Есть нерешённая проблема?

[Создайте заявку](https://github.com/iibaranov-IG/broadcast-control-lab/issues/new?template=repair-request.yml):
модель, прошивка, версия программы, шаги воспроизведения, ожидаемый и фактический
результат. Приложите логи или описание протокола и укажите, можете ли проверить
починку на оборудовании. Удалите пароли и личные данные из материалов.

После проверки нашей сборки сообщите её идентификатор, конфигурацию и результат.
Так следующему пользователю будет понятно, какая комбинация действительно проверена.

## Границы результата

Зелёный прогон подтверждает перечисленные программные проверки конкретной версии.
Реальное оборудование и полный интерфейс приложения проверяются отдельно.
Текущие результаты стенда не являются сертификацией железа; тестовую сборку сначала
проверяют в отдельной конфигурации. UDP-журнал содержит точные байты: используйте
синтетические данные без секретов.

Готовые профили разных производителей, универсальный установщик и автономная
цепочка «issue → PR» ещё не реализованы. БКЛ уже предоставляет работающие стенды,
конкретные починки и повторяемые доказательства. Это самостоятельный проект;
его тестовые сборки не являются официальными релизами производителей.
